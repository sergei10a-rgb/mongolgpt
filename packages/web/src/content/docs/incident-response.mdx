Энэ хуудас нь үйлчилгээ тасрах, нэвтрэх мэдээлэл алдагдах, төлбөрийн төлөв зөрөх, өгөгдөл гэмтэх эсвэл model provider-ийн зардал хэтрэх үед дагах production runbook. Автомат ажиллагаа гэж ойлгохгүй: оператор бодит нөхцөл, аудитын нотолгоо болон зөвшөөрлийг шалгаж алхам бүрийг тэмдэглэнэ.

:::caution[Үйлдвэрлэлийн өөрчлөлтийн зөвшөөрөл]
Production deploy, D1 сэргээх, бодит төлбөр буцаах, provider key солих болон хэрэглэгчид нийтээр мэдэгдэл илгээхээс өмнө бүтээгдэхүүний эзэмшигчийн зөвшөөрөл авна. Идэвхтэй халдлагыг зогсоохын тулд token цуцлах, account түдгэлзүүлэх зэрэг яаралтай хязгаарлалт хийсэн бол шалтгаан, цаг, оператор болон үр дүнг аудитад нэн даруй нөхөж бүртгэнэ.
:::

## Ноцтой байдлыг ангилах

| Түвшин  | Жишээ                                                                                                           | Хариу эхлэх зорилтот хугацаа         |
| ------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `SEV-1` | Нэвтрэлт бүхэлдээ тасарсан, мэдээлэл задрах үндэслэлтэй, буруу төлбөр олноор үүссэн, D1 өгөгдөл гэмтсэн         | Шууд, боломжтой бол 15 минутын дотор |
| `SEV-2` | Нэг үндсэн үйлчилгээ доголдсон, model call олноор амжилтгүй, webhook эсвэл queue удааширсан, зардал огцом өссөн | 30 минутын дотор                     |
| `SEV-3` | Хязгаарлагдмал хэрэглэгчийн алдаа, түр provider саатал, workaround-тай UI доголдол                              | Ажлын 1 өдрийн дотор                 |

Нөлөөлөл өсөх, хэрэглэгчийн өгөгдөл эсвэл мөнгө оролцох, шалтгаан тодорхойгүй удах үед түвшнийг бууруулахгүй, ахиулна.

## Үүрэг ба нэг эх сурвалж

Ослын тасалбар эсвэл хандалт хязгаарласан баримтад дараах үүргийг нэрлэнэ. Жижиг багт нэг хүн хэд хэдэн үүрэг хариуцаж болно, гэхдээ эцсийн production зөвшөөрлийг өөрөө өөртөө олгохгүй.

- **Ослын удирдагч**: түвшин, хамрах хүрээ, дараагийн шийдвэр болон хаах нөхцөлийг тогтооно.
- **Техникийн оператор**: Cloudflare, GitHub Actions, D1, Queue, provider болон аппын нотолгоог шалгаж хязгаарлалт, сэргээх ажиллагааг гүйцэтгэнэ.
- **Аюулгүй байдлын хариуцагч**: credential, account, audit, өгөгдөл задралын эрсдэлийг үнэлж token rotation ба access review-г удирдана.
- **Санхүүгийн хариуцагч**: QPay/Bonum ledger, provider settlement, model cost болон refund-ийн зөрүүг тулгана.
- **Харилцааны хариуцагч**: дотоод шинэчлэл, хэрэглэгчид харагдах төлөв болон хаалтын мэдэгдлийг баталгаатай баримтаар гаргана.

Нэг осолд нэг үндсэн тасалбар ашиглаж, `SEV`, эхэлсэн UTC ба Улаанбаатарын цаг, нөлөөлсөн орчин, үйлчилгээ, одоогийн эзэн, сүүлийн шийдвэр, дараагийн шалгах цагийг хадгална. Нууц түлхүүр, бүтэн token, хэрэглэгчийн prompt, төлбөрийн бүтэн payload болон хувийн мэдээллийг тасалбарт бүү хуул.

## Эхний 15 минут

1. Шинэ өөрчлөлт, production deploy, migration, plan update болон payment reconciliation-г түр зогсооно.
2. [Админ удирдлага](../admin)-ын **Системийн бэлэн байдал**, **Үйлдлийн бүртгэл**, төлбөр ба usage дэлгэцийн timestamp-тай нотолгоог шалгана.
3. `mgpt.mn/api/health`, `auth.mgpt.mn/health`, `runtime.mgpt.mn/global/health`, `pay.mgpt.mn/health` хариуны HTTP төлөв, content type болон schema-г бүртгэнэ. Response body-д нууц мэдээлэл байвал тасалбарт бүү оруул.
4. Cloudflare-ийн service status, Worker/Container/D1/Queue/R2 health, GitHub Actions-ийн сүүлийн deploy commit болон provider-ийн албан ёсны status-ийг тулгана.
5. Нөлөөлсөн account, workspace, invoice эсвэл request ID-г хамгийн бага шаардлагатай хүрээнд тогтооно. Бусдын өгөгдөлтэй нийлүүлж задруулахгүй.
6. Ноцтой байдлыг сонгож, ослын удирдагч болон дараагийн шинэчлэлийн цагийг нэрлэнэ.
7. Шалтгаан батлагдахаас өмнө DNS, database, provider key болон төлбөрийн төлвийг олон дахин зэрэг өөрчлөхгүй.

## Хязгаарлах ажиллагаа

### Нэвтрэлт эсвэл credential алдагдал

1. Нөлөөлсөн account/админы эрхийг түдгэлзүүлж, хэрэглэгчийн API key болон сессийн `authVersion`-ийг цуцална.
2. GitHub, Cloudflare, OpenRouter, NVIDIA, QPay эсвэл Bonum-ын нөлөөлсөн token/key-г тухайн үйлчилгээ дээр нь revoke хийнэ. Шинэ утгыг зөвхөн зориулалтын secret store-д хадгална.
3. Шинэ credential-ийг deploy хийхээс өмнө эрхийг хамгийн бага хүрээнд тохируулж preflight ажиллуулна.
4. Audit log, Cloudflare Access болон provider access log-оор алдагдсан credential ашиглагдсан хугацаа, хамрах хүрээг тогтооно.

### Төлбөрийн зөрүү

1. Нэг invoice/webhook-ийг гараар `paid` гэж засахгүй, дахин webhook зохиож илгээхгүй.
2. QPay/Bonum provider status, immutable invoice/event ledger, Queue болон entitlement төлвийг external invoice ID ба дүнгээр тулгана.
3. Үр дүн тодорхойгүй refund-ийг дахин бүү үүсгэ. Админ дахь provider-check эсвэл state-resume үйлдлийг ашиглана.
4. Давхар төлбөр, буруу entitlement эсвэл provider settlement батлагдвал нөлөөлсөн хэрэглэгчийн жагсаалт, нийт дүн, засварын receipt-ийг тусад нь хадгална.

### Model зардал, quota эсвэл abuse

1. Нөлөөлсөн account/workspace-г түдгэлзүүлэх эсвэл plan/provider route-г алдаанд хаалттай горимд оруулна.
2. Durable Objects quota ledger, usage queue, бодит provider usage болон санхүүгийн cost ledger-ийг нэг хугацааны цонхоор тулгана.
3. Provider key-г client log-д гаргахгүй; шаардлагатай бол provider талд key-г revoke/rotate хийнэ.
4. Шалтгаан арилтал limit-ийг өсгөх, Free Auto fallback-ийг хязгааргүй болгох эсвэл BYOK usage-г MongolGPT-ийн зардал мэт тооцохгүй.

### Өгөгдлийн гэмтэл

1. Бичих endpoint, payment queue consumer болон migration-г түр зогсоож, одоогийн D1 bookmark/экспортыг хамгаална.
2. Сүүлийн хүчинтэй R2 manifest, SQL object, D1 Time Travel цэг болон migration version-ийг шалгана.
3. [Нөөцлөлт ба сэргээх](../backup-restore)-ийн plan-only алхам, яг тохирох confirmation болон эзэмшигчийн зөвшөөрөлгүйгээр restore бүү ажиллуул.

## Нотолгоо хамгаалах

- Git commit SHA, workflow run ID, deploy stage, үйлчилгээний нэр, UTC timestamp, request/invoice ID болон bounded error code хадгална.
- Audit, Queue, Worker, Access болон provider log-ийн эх хувийг өөрчлөхгүй. Шаардлагатай экспортод хандалтын хугацаа ба эзнийг тэмдэглэнэ.
- Нууц token, authorization header, cookie, provider raw payload, prompt болон source code-г ердийн чат, нийтийн issue эсвэл screenshot-д бүү оруул.
- Өгөгдөл хадгалах хугацаа болон устгах хүсэлтийг [Нууцлал](../privacy)-ын бодлоготой нийцүүлнэ.

## Харилцаа

Дотоод шинэчлэлт бүрт батлагдсан нөлөөлөл, одоо хийж буй нэг ажиллагаа, хэрэглэгчийн аюулгүй хийх зүйл, дараагийн шинэчлэлийн цагийг бичнэ. Таамгийг баримт мэт бүү нийтэл.

Хэрэглэгчид харагдах мэдэгдэлд нууц техникийн мэдээлэлгүйгээр:

```text
MongolGPT-ийн <үйлчилгээ> хэсэгт <эхэлсэн цаг>-аас доголдол илэрлээ.
Нөлөөлөл: <батлагдсан хэрэглэгчийн үйлдэл>.
Бид <хязгаарлах/сэргээх ажиллагаа>-г хийж байна.
Дараагийн шинэчлэл: <цаг>.
```

Сэргэсний дараа бодит баталгаажуулалтын үр дүн, үлдсэн хязгаарлалт болон хэрэглэгчээс шаардах алхам байгаа эсэхийг тодорхой бичнэ.

## Сэргээх ба баталгаажуулах

1. Root cause эсвэл аюулгүй workaround батлагдаж, хязгаарлалт хэрэгжсэн байна.
2. Засварыг dev орчинд typecheck, unit/integration, security болон browser smoke-оор шалгана.
3. [Хувилбар шинэчлэх ба буцаах](../release-upgrade)-ын production confirmation, immutable commit болон rollback цэгийг батална.
4. Health endpoint бүр зөв schema/content type-тэй; login/logout/session, нэг бодит эсвэл sandbox model call, quota/usage, payment sandbox болон admin access урсгалыг хамрах хүрээнд нь шалгана.
5. Queue backlog, provider error/cost, D1 mutation, payment ledger болон audit-д шинэ зөрүү үүсээгүйг ажиглана.
6. Эхлээд хязгаарлагдмал traffic эсвэл операторын account-аар canary шалгаад дараа нь ердийн урсгалыг нээнэ.
7. Хяналтын цонх дуустал incident-ийг `resolved` болгохгүй. Түр workaround үлдсэн бол `mitigated` төлөвтэй байлгана.

## Хаалт ба дараах дүгнэлт

`SEV-1` болон `SEV-2` осол бүрт дараахыг баримтжуулна:

- хэрэглэгч, мөнгө, өгөгдөл болон хугацааны бодит нөлөөлөл;
- илрүүлэлтээс хязгаарлалт, сэргээх хүртэлх timeline;
- үндсэн шалтгаан ба нөлөөллийг нэмэгдүүлсэн нөхцөл;
- сайн ажилласан хамгаалалт болон илрээгүй/ажиллаагүй gate;
- эзэн, хугацаа, шалгах тесттэй засварын ажлууд;
- alert, runbook, rollback, backup restore болон access review-д оруулах өөрчлөлт.

Дүгнэлт нь хүн буруутгах бус системийн хамгаалалт, илрүүлэлт, шийдвэрийн чанарыг сайжруулахад чиглэнэ. Нээлттэй засвар бүр issue эсвэл ажлын бүртгэлтэй, эзэн ба дуусах шалгууртай байна.
